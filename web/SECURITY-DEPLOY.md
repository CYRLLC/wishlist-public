# Security update deployment

This update changes authentication boundaries. Deploy the functions, updated web build and rules together in a short maintenance window. Older web/iOS clients that directly create couples or point transactions will be rejected by the new rules.

## Changes

- User profiles can only be read by the owner or their actual partner. Only nicknames can be edited from the browser.
- Couple membership is created on the server with a single-use invitation that expires after 24 hours. Creating a new invitation invalidates the previous one. User IDs and old invitation links no longer work as invitations.
- Task awards and wish redemption use server-side transactions with membership, reviewer, status and balance checks. Repeated requests cannot award/spend twice.
- Images are stored under the couple and uploader IDs. The UI loads them through an authenticated function; no public download URLs are generated by the app.
- Old image paths cannot be downloaded through client Storage APIs. The administrator migration sets the owning couple in private file metadata, which the image function checks. Copying someone else's old image URL into a new record does not grant access.

## Deployment

The clean public repository is `CYRLLC/wishlist-public`; the original `CYRLLC/wishlist` stays private because GitHub may retain cached old commits. Firebase remains the same project and existing data is preserved. The public repository's GitHub workflow runs isolated security tests, builds and publishes Pages. It contains only Firebase Web config secrets, not an administrator service account key. Deploy backend functions and rules separately with Firebase CLI as below. Use a maintenance window because older clients will stop working when the rules change.

From `web/` (Node.js 22):

```powershell
npm ci
npm run typecheck
npm run build
npm --prefix functions ci
npm --prefix functions run build
firebase deploy --only functions:createPairInvite,functions:acceptPairInvite,functions:settlePoints,functions:readPrivateImage --project wishlist-87fd1
```

Publish the new web build through the GitHub Pages workflow, then deploy the rules:

```powershell
firebase deploy --only firestore:rules,storage --project wishlist-87fd1
```

The existing Cloud Functions setup requires billing enabled; these additional functions can incur usage charges. The code does not change the billing plan.

## Revoke existing public image links

Changing rules alone does not revoke previously issued download tokens. Use an administrator's Application Default Credentials (`gcloud auth application-default login`), then run from `web/functions/`:

```powershell
node scripts/revoke-image-tokens.cjs wishlist-87fd1 wishlist-87fd1.firebasestorage.app --dry-run
node scripts/revoke-image-tokens.cjs wishlist-87fd1 wishlist-87fd1.firebasestorage.app --apply
```

This rotates download tokens to new undisclosed values, without deleting images or records, and assigns ownership metadata from the existing wish/expense references. Files referenced by multiple couples or without a known owner stay blocked until administrator review. Review existing records for suspected forged references before applying the migration. The updated authenticated reader supports the original image URLs stored in existing records after ownership is assigned and the old tokens are revoked. Run during the maintenance window so the old UI does not rely on the revoked links.

Before reopening the site, verify that an old token URL no longer loads in an unauthenticated browser, while both partners can still view that image through the updated app. Previously downloaded copies cannot be revoked.

The local Storage emulator appends new tokens to its internal token list when metadata changes. The automated test verifies metadata rotation, ownership assignment and file preservation; it cannot confirm real download-link invalidation. The unauthenticated production URL check above is required after migration.

## Existing pairings

Existing consistent pairings remain valid. Review each existing couple's members and both profiles' coupleId fields in the Firebase Console, because old rules allowed unauthorized edits. Do not automatically restore a profile to the first historical couple: that record may have been forged. An administrator should correct inconsistent pairings only after confirming both owners.

## Regression checks

Use the emulator security tests for anonymous/outsider denial, profile isolation, immutable couple membership, server-only points, invitation expiry/reuse, duplicate point requests, and image restrictions. Tests never use the production database.

Install Firebase CLI and Java 21, then run `npm run test:security` from `web/`. The emulators use the isolated project `demo-wishlink-security`.
